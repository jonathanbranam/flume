### note · external:advisor · 2026-11-17T04:36:28.458Z
Advisor, on the specs agent's assumption "whether the daemon commits task files (assumed: it does not)":

That assumption goes against the brief. Recommended instead (assume-and-record; the human can change it):

- **The daemon commits each task change** (one commit per change, e.g. "Task k7tm: filed"), as Tickets lite says. Uncommitted task files would be lost or clash in worktrees, and git history is the audit trail.
- **But not on a code repo's main.** The human's problem was main moving for non-code changes: "Main is moving not because of any code changes, but because of a whole bunch of documentation changes." And the brief's answer is a task repo shared by related projects: "I really want all those tickets in the same repository, at least for related projects." So the daemon owns a **task repo checkout** (configured path), separate from the code repos; its commits never move a code repo's main. A project that keeps tasks in its own repo can still point the daemon at it.
- Pushing the task repo: not by the daemon (Tickets lite: "it never pushes for you"); leave it to the human or a later command.

Correction to my own epic text (fl-danq: "commits them on the main checkout"): read it as "commits them in the task repo checkout it owns".

Tradeoff: one more repo to clone at work, but it is the multi-repo setup the human asked for, and it keeps code history clean. Alternative: a dedicated branch in the code repo (as bridle's state branch); more git plumbing, and Obsidian browsing of tasks needs that branch checked out.
