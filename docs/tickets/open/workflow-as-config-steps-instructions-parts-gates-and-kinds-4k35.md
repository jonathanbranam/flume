## The ask

Flume ships several workflows, and a user can fully override any part of the workflow system and
replace it with their own, the way OpenSpec's schemas work: a workflow declares its steps, each
with its instructions, template and dependencies. A workspace and a project have one default
workflow; a project maps ticket kinds to workflows (one default for every kind, a specific one for
specific kinds); a ticket can choose a different workflow. fl-94yx removes the rigid built-in
phases first; this ticket brings workflow back as config, slowly, carefully, one step at a time.

## Design

Not designed yet. The way back, one step per child ticket, each shipped and used before the next
is designed:

1. **Steps declared.** A workflow file in the flume root (layered like the other documents:
   shipped, workspace, project) lists the workflow's steps by name. A task records its current
   step; flume accepts only the steps the workflow declares. flume workflow prints the workflow as
   configured (it printed the fixed five phases before fl-94yx).
2. **Instructions per step.** Each step names its instruction text; flume task instructions and
   claim print the current step's instructions, generated by flume from the config (this replaces
   the old phases.md).
3. **Required parts and templates.** A step names the part it writes and that part's template.
   Ad hoc parts stay allowed beside the required ones.
4. **Dependencies and the forward gate.** A step lists what it requires (a graph, not only a
   line, as in OpenSpec); the gate that refuses an agent moving forward without reading the
   instructions comes back, switched on by config.
5. **Workflow per kind and per task.** A project's default workflow and a map from kind to
   workflow (fl-h8ty); a task may name its own workflow.
6. **Guides and steps** (open): whether guides attach to steps again (they were pushed to phases
   before fl-94yx) and how they relate to the plan's Guide: lines.

Open, to settle in step 1 or later: whether users can configure plans (the plan form stays as
flume defines it for now); the workflow file's format (YAML like OpenSpec's schema.yaml, or
Markdown); the model is docs/research/openspec.md.

## Discussion (for reference, not authoritative)

The human, 2026-11-25 (to advisor), verbatim:

> The end state is: flume ships several workflows, but the user can fully override any part of the workflow system and replace it with their own. That means that flume cannot make strong assumptions about the workflow itself. However, the shape and design of fully config-driven and overrideable workflows is large.
>
> Flume should behave similarly to openspec in this regard: openspec has a standard workflow driven by its artifacts which declare their instructions, templates, and dependencies, but all of which can be replaced by a different "scheme" There is one default "scheme" (our workflow) for a workspace + project and then each ticket can choose a different workflow. In flume also I would allow a map from kind to workflow so a project can configure one default workflow for all ticket kinds, then a specific workflow for specific ticket kinds.

Then, on removing the rigid phases (fl-94yx):

> The solution as-built is not incorrect, it is just too rigid. So, we will need to come back in a subsequent ticket and implement "workflow as config". As you're removing this rigid implementation, make that ticket and note how we should re-introduce workflow in the future. We should introduce it slowly, carefully, one step at a time.
>
> 1. agree to remove; in the future, valid phases will be configured per workflow;
> 2. forward gate will definitely be re-introduced, through configuration
> 3. per-phase instructions will be part of future solution
> 4. seems fine to remove

> 6. I think even in destination state, a user of flume can create adhoc task parts. The workflow-as-config would list the required parts and templates
